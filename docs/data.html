The Data

GhostTrack pulls from 4 different data sources. Here's where each one comes from, what it contains, and why we need it.

The 4 Data Sources

1. Spotify API

The official Spotify API provides metadata about artists, albums, and tracks. We use it to fetch release dates, track names, follower counts, and (when available) audio features.

What still works (April 2026): artist search, album list, track list, artist metadata

What was restricted (Feb 2026): /audio-features, /recommendations, related artists

How we use it: Main source for the live pipeline (any artist search). Cached responses stored in data/raw/cache/ as JSON files.

Setup needed: SPOTIFY_CLIENT_ID and SPOTIFY_CLIENT_SECRET in .env

2. Kaggle Dataset (114,000 Tracks)

3. Neo4j AuraDB (Graph Database)

A cloud graph database that stores our 4 seed artists and all their relationships.

What is a graph database?
A regular database (like Excel) stores rows and columns. A graph database stores nodes (things) and edges (relationships between things). It's perfect for questions like "which production company registered the most tracks for this artist?" because those are naturally graph-shaped questions.

Database schema (the shape of the data)

(Artist) -[:RELEASED]-> (Album) -[:CONTAINS]-> (Track) -[:REGISTERED_WITH]-> (ProductionCompany) Artist properties: spotify_id, name, followers, popularity Album properties: spotify_id, name, release_date, total_tracks Track properties: spotify_id, name, isrc, duration_ms Company properties: isrc_prefix, country_code, registrant_code

4. YouTube API + iTunes API

Used for Signal 7 (Cross-Platform Detection).

  • YouTube Data API v3: Searches for the artist name, returns view count of the top video. Requires YOUTUBE_API_KEY in .env.
  • iTunes Search API: Free, no authentication needed. Checks whether the artist appears in an iTunes search. Returns artist name, genre, and Apple Music link if found.

API Caching — How We Save Money and Time

Think of it like taking notes from a library book.
You don't check out the same library book every day to re-read the same passage. You write down the important parts once. Our API cache does the same: the first time we fetch an artist's albums, we save the response as a JSON file. Next time, we read from the file instead of calling the API again. This keeps us under rate limits and makes the app fast.

Cache location: data/raw/cache/
Format: artist_{artist_id}_albums.json, album_{album_id}_tracks.json, etc.
Cache entries never expire (you must delete them manually to force a refresh).

Processed Data Files

Every exercise saves its outputs to data/processed/. Here's what each file contains:

ex1_catalog_features.csv

Per-track audio features (danceability, energy, valence, acousticness) for the 6 artists analyzed in Exercise 1.

ex1_variance_table.csv

Per-artist total variance summary. The key Signal 1 output table.

ex2_entropy_table.csv

Shannon entropy scores for 3 playlist archetypes (editorial, fan-curated, ghost-suspect).

ex2_playlist_features.csv

Track-level audio features for all tracks in all 3 playlists analyzed in Exercise 2.

exercise4_metrics.csv

HHI and ISRC concentration metrics per artist (the main Signal 6 table).

exercise4_ghost_neighborhood.json

The bipartite graph structure in JSON — nodes are artists + companies, edges are track registrations.

exercise5_walk_metrics.csv

Release cadence metrics: closure rate, median gap, burst ratio per artist.

exercise5_walk_graphs.json

Temporal release event sequences for each artist — used to draw the cadence histograms.

ex6_signal_report_card.csv

All 7 signal scores for all 4 artists in one table. The main Exercise 6 output.

ex6_verdicts.json

Final verdict (LIKELY_GHOST, SUSPICIOUS, LIKELY_ORGANIC) + confidence + explanation for each study artist.

ghost_candidates_kaggle.csv

~50 artists from Kaggle with very low audio variance and high track counts — ghost candidates (heuristic, not confirmed).

organic_controls_kaggle.csv

~50 artists from Kaggle with high audio variance — used as organic controls in the GNN training set.

gnn_dataset.pt

The PyTorch Geometric graph dataset: 65 nodes, 8 features each, 692 edges, train/val/test masks.

gnn_dataset_meta.json

Metadata for the GNN dataset: feature names, node names, ghost/organic labels, dataset statistics.

gat_model.pt

Trained Graph Attention Network weights. Load with torch.load('gat_model.pt').

gcn_model.pt

Trained Graph Convolutional Network weights (baseline model).

gnn_training_summary.json

Training results: accuracy per epoch, final ROC-AUC, confusion matrix, feature importance scores.

Environment Variables (.env file)

The project needs these secret keys to access external APIs. They go in a file called .env in the project root (never committed to git):

# Copy this from .env.example and fill in your keys
SPOTIFY_CLIENT_ID=your_client_id_here
SPOTIFY_CLIENT_SECRET=your_client_secret_here

NEO4J_URI=neo4j+s://xxxxx.databases.neo4j.io
NEO4J_USER=neo4j
NEO4J_PASSWORD=your_password_here

OPENAI_API_KEY=sk-...
YOUTUBE_API_KEY=AIza...

# Optional: custom path to Kaggle dataset
KAGGLE_DATASET_PATH=data/kaggle/dataset.csv
Never share your .env file — it contains private API keys. The .gitignore file already ensures it won't be committed to GitHub by accident.
